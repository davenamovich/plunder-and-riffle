CORE ECONOMIC MODEL
==================================================

This system is built on one simple idea:

- free spots prove the value
- paid spots scale the value

Each qualifying signup gives the user 24 hours in the agent rotator.

There are two rotator slot types:

1. FREE SPOTS
- unlocked by joining the qualifying offer
- 24-hour duration
- proof-of-value
- one active free slot per user per agent

2. PAID SPOTS
- optional
- 24-hour duration
- dynamically priced based on demand
- weighted higher than free spots
- intended to scale what is already working

Core economic anchor:
“What is a real human lead worth?”

These are Web2 offers that only humans can complete.
Agents cannot complete them.
Agents generate and route intent.
Humans complete the action.
The system captures and distributes the value.

TWO ROTATOR MODEL
==================================================

This MVP has two distinct rotators:

1. AGENT ROTATOR
2. PERSONAL ROTATOR

==================================================
1. AGENT ROTATOR
==================================================

The agent rotator is the main public traffic rotator.

Purpose:
- generate signups for the offer
- prove traffic value to users
- distribute incoming traffic
- create free-to-paid upgrade pressure
- act as the main monetization engine

Rules:
- every user who signs up for the qualifying offer gets 24 hours in the agent rotator
- the agent rotator has free and paid spots
- each spot lasts 24 hours
- paid spots receive stronger weighted exposure than free spots
- incoming traffic to the agent landing page is routed to the next eligible user in the agent rotator
- if no eligible rotator user exists, fallback goes to the base offer / house link / admin link

Suggested MVP defaults:
- 25 free slots
- 25 paid slots
- free weight = 1
- paid weight = 3
- duration = 24 hours
- weighted round robin routing
- deterministic server-side state
- one active free slot per user per agent
- one active paid slot per user per agent unless admin changes it

2. PERSONAL ROTATOR
==================================================

Every user gets a PERSONAL ROTATOR.

Purpose:
- let users monetize their own network further
- create a shareable personal page
- act like a dynamic referral-aware link tree
- rotate through the offers and links the user should share
- preserve inherited referral logic
- give the user one master page to distribute

The personal rotator should:
- show or rotate through the offers the user has access to
- use the correct inherited referral links
- update automatically as the user signs up for more offers
- let the user share one page that monetizes their audience

The personal rotator is not just a profile page.
It is a monetization surface.

==================================================
REFERRAL INHERITANCE LOGIC
==================================================

This is a critical first-class feature.

When a new user signs up under a referrer:
- the new user should use the referrer’s links for every offer the referrer has already joined
- those inherited links should populate the new user’s personal rotator
- if the new user signs up for those offers, attribution should reflect the inherited upstream referral logic
- this creates a compounding network effect

Example:
- Referrer has joined Offer A, Offer B, Offer C
- New user joins through that referrer
- New user’s system-generated signup links for those offers should use the referrer’s referral URLs or tracked inherited equivalents
- new user can then share their own personal rotator, which is aware of the proper upstream logic

The system should behave like a smart, live, monetized link tree.

==================================================
RALPH LOOP + MOLTIS
==================================================

The Ralph loop should run through Moltis, but results must be written back into our app/database.

Flow:
1. candidate leads are ingested by the app or worker
2. candidates are stored in Postgres
3. batches are queued in Redis
4. Moltis consumes a batch job through a thin adapter layer
5. Moltis runs classification/scoring logic
6. Moltis returns structured results
7. app stores those results in Postgres
8. drafting jobs are queued
9. Moltis drafts comments
10. drafts are stored in Postgres
11. admin approves or future rules auto-post them
12. resulting actions and KPIs are logged back into Postgres

Do not tightly couple app logic directly to Moltis internals.
Use a thin adapter/service boundary.
